# Feature Specification: Persistent Pico2 Multi-Pool KES Agent

**Feature Branch**: Not created; no branch-creation hook configured.

**Created**: 2026-10-27

**Status**: Ready for planning — operator policies resolved.

**Input**: Implement a minimal Cardano KES agent on the accepted Pico2 A2 device, with Rust firmware and a Rust systemd service named `pico2-kes-agentd`. Persist, evolve, and rotate keys for 64 simultaneous pools; allow clients with socket access to obtain and manage every configured pool's keys. Extend the local cardano-node bulk credentials to support the agent. Export each newly generated initial KES key securely for a conventional file-based backup producer. Clarified decisions: full socket-based management authority; one shared recipient private key held on the backup host; activation after encrypted export without backup-readiness checks; separate per-pool Unix sockets permitted to simplify node integration. Use the prior Pico HSM plan and cardano-kes-forge export workflow as evidence, not inherited requirements. This feature is a specification, not an implementation claim.

## Clarifications

### Session 2026-10-27

- Q: When a pool already has a replacement KES key waiting for its certificate or start period, what should happen if you request another replacement? → A: Reject the new generation request until the operator explicitly discards the staged generation through the CLI; discard removes only that replacement's operational key and leaves the active generation unchanged.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Recover pool keys after complete power loss (Priority: P1)

A pool operator commissions the device, creates a pool's KES key on it, obtains a matching operational certificate using the existing offline cold-key process, and starts a producer. After both host and device lose power, the producer obtains the same generation at its current valid period without a replacement certificate or secret recovery file on the primary host.

**Why this priority**: Durable recovery without retaining obsolete operational keys is the reason for this device.

**Independent Test**: Using disposable credentials, generate and certify one pool, advance it, remove power from host and device, restore both, and demonstrate valid signing with the recovered generation and unchanged verification key/certificate.

**Acceptance Scenarios**:

1. **Given** a certified active key at relative period 5, **When** power is restored during relative period 8, **Then** the device catches up to 8 before releasing a key and preserves the generation, verification key, and certificate.
2. **Given** an interrupted evolution or rotation, **When** the device recovers, **Then** it resolves a single authoritative state, completes obsolete-state erasure before release, and never restores a state older than an acknowledged transition or released successor.
3. **Given** the only active generation expired during an outage, **When** services recover, **Then** the pool is reported expired; no expired key is delivered, no new generation is silently created, and unrelated valid pools remain usable.
4. **Given** unavailable or inconsistent period information, **When** the host reconnects, **Then** no new time-dependent key delivery or evolution occurs until the information is valid; no period is guessed and no state is rolled back.
5. **Given** failed erasure or ambiguous/corrupt pool storage, **When** recovery runs, **Then** that pool is unavailable with an actionable reason rather than automatically reset; healthy pools continue unless shared device state is affected.

### User Story 2 - Operate 64 pools through one device (Priority: P1)

An operator configures a bulk block producer to use one device through one daemon, with a distinct node-service socket path for each pool. Each credential selects its pool's socket. All pool sockets and the daemon's management socket share the same access permissions: authorized clients can obtain any pool's operational key and perform all management operations. There are no per-pool passwords, pool-specific access-control lists, or additional administrator credentials.

**Why this priority**: Capacity and multi-pool routing are core requirements, not later scaling work.

**Independent Test**: Configure 64 independently certified pools in a single bulk producer, obtain all 64 matching key/certificate pairs, and prove pool-correct signing before and after reconnect and rotation.

**Acceptance Scenarios**:

1. **Given** 64 enrolled pools, **When** all are requested concurrently through their configured pool sockets, **Then** each receives only that socket's pool and current valid generation, with no starvation or cross-pool substitution.
2. **Given** a client with the configured socket access, **When** it connects to any pool socket or the management socket, **Then** it is not asked for additional credentials; a client without that access cannot obtain keys or manage pools.
3. **Given** all 64 slots are occupied, **When** an operator tries to enroll a 65th pool, **Then** enrollment is rejected without changing any existing pool.
4. **Given** bulk credentials containing both file-based and agent-backed pools, **When** the node starts or reloads credentials, **Then** each uses its selected source; an unavailable agent-backed pool does not prevent healthy pools from operating or silently switch that pool to a file.
5. **Given** legacy file credentials or the existing single-pool agent configuration, **When** the updated node loads them, **Then** their existing meaning is preserved. Existing external-signing bulk credentials are not removed or reinterpreted.
6. **Given** unknown, duplicate, malformed, or certificate-mismatched pool selection, **When** configuration is loaded or a key is requested, **Then** the operation fails with the affected entry or pool identified and no wrong-pool key released.
7. **Given** a client with socket access, **When** it enrolls a pool, generates a key, installs a valid certificate, changes the shared backup recipient, or deletes a pool, **Then** the operation requires no separate administrator or offline approval; state, certificate, and integrity checks still apply.

### User Story 3 - Rotate keys without interrupting unrelated pools (Priority: P1)

An operator prepares a replacement generation and encrypted initial-key export while the current generation continues serving the pool. Export automatically authorizes activation; the operator obtains the matching certificate through the existing external process, and the replacement activates as soon as that certificate is valid and its start is reached. There is no separate activation approval or dependency on the backup host, archival, or restore verification. Ordinary evolution requires neither a new generation nor a new certificate.

**Why this priority**: KES generations expire; predictable replacement is necessary for sustained operation.

**Independent Test**: Prepare and activate a replacement for one of 64 operating pools, including a lost command reply and a restart, and prove that the replacement is published once while the other 63 pools remain correct.

**Acceptance Scenarios**:

1. **Given** an active generation, **When** its replacement's encrypted export is committed and its matching certificate is valid at the current period, **Then** the replacement activates automatically without a backup acknowledgment or separate activation command; until those prerequisites hold, the previous valid generation remains usable.
2. **Given** an acknowledged generation whose reply or artifact download is lost, **When** the same operation is retried, **Then** the existing generation and byte-identical artifact are recovered rather than generating another key.
3. **Given** an exported replacement with a future certificate start, **When** that start is reached with valid period information, **Then** the replacement activates automatically without consulting the backup host; early key publication is prohibited. An exported replacement without a certificate similarly waits only for valid certification and timing, not backup readiness.
4. **Given** a wrong-pool, wrong-generation, invalidly signed, expired, or regressive replacement certificate, **When** it is submitted, **Then** it is rejected without replacing the valid active key.
5. **Given** a crash after activation became durable but before the node learned of it, **When** service resumes, **Then** the committed replacement is delivered without resurrecting the superseded generation or requiring a node restart.
6. **Given** active and staged generations for all 64 pools, **When** periods advance, **Then** all started, certified generations advance or expire independently. Uncertified generations remain at period zero; an expired staged generation cannot activate.
7. **Given** an exported, currently valid replacement and an offline backup host, **When** activation runs, **Then** it succeeds without an archival receipt, decryption attempt, backup notification, or confirmation that a conventional backup file exists.
8. **Given** an encrypted export from a disposable device-generated KES generation, **When** it is decrypted with the recipient key and restored to the conventional KES signing-key file format, **Then** the recovered key state matches the device's original period-zero state byte-for-byte, and an independent standard-format decoder reads that same state from the file. This check requires no running backup block producer.
9. **Given** an occupied staged-generation slot, **When** another generation is requested, **Then** the request is rejected without changing either generation; after the operator explicitly discards the identified staged generation through the CLI and cleanup completes, a new replacement can be generated without changing the active key.
10. **Given** a discard naming a staged generation, **When** that generation has already activated or the slot now contains a different generation, **Then** the discard cannot erase either the active key or the different staged key; retrying a completed discard only reconciles the original result.

### User Story 4 - Run and diagnose the service unattended (Priority: P2)

The operator installs the host service and `pico2-kes-agent-cli`, assigns socket permissions, and uses the utility to inspect device/pool status and perform the supported maintenance operations. The operator can distinguish a disconnected device, delayed evolution, expired pool, and storage failure without seeing secret material in logs. Reboot or USB reconnection does not require a runtime PIN or manual reconstruction of keys.

**Why this priority**: The durable-key benefit must survive ordinary operational interruptions, not only a controlled demonstration.

**Independent Test**: Use the installed utility to inspect status and perform the supported pool lifecycle operations through the deployed daemon, then restart and reconnect the service/device while a node is operating. Observe socket ownership, recovery, reported command outcomes, and the absence of plaintext durable key files on the primary.

**Acceptance Scenarios**:

1. **Given** the configured service is enabled, **When** the host boots or the service restarts, **Then** it owns the configured per-pool node-service sockets and management socket with identical access permissions, reconnects to the intended device, and resumes valid subscriptions without operator intervention.
2. **Given** a node already holds a valid key, **When** USB or daemon service is lost, **Then** the node is not stopped and is not told its key was deleted merely because the device is unavailable.
3. **Given** an occupied endpoint or unexpected device identity, **When** the service starts, **Then** it reports the conflict rather than taking over another live service or trusting the wrong device.
4. **Given** a slow or malformed client, **When** other clients request healthy pools, **Then** resource consumption remains bounded and healthy clients continue to be served within the stated targets.
5. **Given** ordinary operation or an error, **When** logs and durable primary-host outputs are inspected, **Then** no plaintext operational KES keys, generation seeds, backup decryption credentials, or secret-bearing traffic are present.
6. **Given** an operator with socket access, **When** the utility lists pools, reads device/pool status, enrolls a pool, generates a key, retrieves its verification key and encrypted export, installs its certificate, discards an identified staged generation, changes the shared recipient public key, or deletes a pool, **Then** the daemon performs the operation under the existing lifecycle rules without direct USB access by the utility or additional credentials. Rotation retains export-triggered automatic activation.
7. **Given** a denied socket connection, unavailable daemon/device, rejected operation, or lost reply, **When** a management command runs, **Then** the utility reports the failure or uncertain outcome with a non-success exit status, never silently connects directly to USB, and preserves the operation identity needed to reconcile a retry without duplicate generation.
8. **Given** an encrypted artifact and the recipient private key on the backup host, **When** the utility performs local restoration with no daemon, device, or backup producer running, **Then** it produces the conventional KES key file under FR-011 and SC-006 without transmitting the recipient private key or decrypted state to the service.

### Edge Cases

- Power loss during initial generation, certification, evolution, activation, deletion, or obsolete-state cleanup: recover the authoritative generation or report unavailable; never invent success or erase the sole recoverable state before a successor is durable.
- Reply lost after a durable operation: reconcile its identity before attempting any new mutation; never turn a timeout into another generation.
- Device unpowered across several periods: erase delayed obsolete state and catch up before delivery; no claim of evolution or erasure while unpowered.
- Host period regression, unavailable network context, stale chain information, or future certificate start: withhold time-dependent delivery rather than guess, rewind, or expire prematurely.
- Network-specific lifetime versus the KES primitive's limit: use the configured network validity; pool count 64 is unrelated to the primitive's 64 periods.
- All pools evolving at a boundary while replacements are prepared: retain 64-pool capacity and prevent one pool or client from monopolizing service.
- Concurrent requests for one pool during rotation: each response describes one internally consistent generation, period, and certificate; no mixed-generation bundle.
- Staged-generation conflicts: a new generation request never implicitly overwrites an occupied staged slot. Explicit discard cancels that generation's pending activation and erases its operational secret without touching the active key. If activation wins a race with discard, discard fails rather than deleting the now-active key; stale retries cannot discard a later staged generation.
- Deletion followed by slot reuse: the new pool cannot receive residual old secrets or inherit another pool's identity. External encrypted backups are not revoked by slot reuse.
- Backup recipient loss: existing ciphertext is not recoverable through a plaintext bypass or recipient override; prepare a new generation and certificate if no usable backup remains.
- Backup unavailable at rotation time: activate the exported replacement once its certificate and period are valid, regardless of backup availability. Do not require archival, restoration, or a remote acknowledgment, and do not extend the old certificate's validity.
- Socket-client compromise: the attacker has full lifecycle authority over all pools and can delete keys or redirect future encrypted exports. This accepted trust model does not promise protection from valid but malicious management commands.
- Multiple producers possessing the same pool's key: access does not imply fencing; operators must prevent simultaneous primary/backup forging.
- Flash exhaustion, unsupported fitted storage, failed entropy, and irreversible hardware failure: report unavailability without weak randomness, secret import, silent reinitialization, or claimed guaranteed recovery.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001 — Minimal key-provider boundary**: The device MUST generate, persist, evolve, rotate, and retire Cardano-compatible KES state; the node MUST receive the current state and perform its own signing. General HSM functions, cold-key custody, and device-side block signing are outside scope. Acceptance: Stories 1, 3, and 4; no device request is required for each block after successful delivery.
- **FR-002 — Capacity**: One device MUST support 64 enrolled pools simultaneously, each with one active and one staged replacement generation, including their certificates and encrypted generation-time backups. A 65th enrollment MUST fail without eviction. Acceptance: Story 2 scenarios 1 and 3; Story 3 scenario 6.
- **FR-003 — Pool routing and common access**: The daemon MUST expose a distinct node-service socket for each pool, with a stable mapping between socket path and pool identity. All pool sockets and the management socket MUST share the same access policy, without separate per-pool credentials. A client selects a pool by connecting to its socket; no shared-stream pool selector is required. Unknown or mismatched configuration MUST fail without substitution. Acceptance: Story 2 scenarios 1, 2, and 6.
- **FR-004 — Bulk and legacy interoperability**: The local node MUST support agent-backed entries in bulk credentials, each specifying its pool's socket path, including mixtures with file-based entries. The node-service sockets MUST preserve the existing KES-agent service behavior rather than require a new multi-pool wire protocol. Existing legacy file, singleton-agent, and external-signing configurations MUST retain their meaning. Agent unavailability MUST NOT trigger an implicit file fallback. Acceptance: Story 2 scenarios 4–6.
- **FR-005 — Current-state durability**: A successful state-changing operation MUST survive complete ordinary host/device power loss. Recovered key state MUST never precede an acknowledged transition or a released successor. Recovery MUST complete required cleanup and catch-up before key delivery. Acceptance: Story 1 scenarios 1–3 and Story 3 scenario 5.
- **FR-006 — Obsolete-secret removal**: Obsolete operational state, abandoned secret candidates, and temporary generation seeds MUST be removed before a successor is acknowledged or released. Recovery MUST finish interrupted cleanup; unverifiable erasure MUST prevent affected key release. The erasure claim MUST be bounded to the fitted device storage's qualified erase/read behavior, not file deletion or encryption alone. Deliberately retained encrypted backups and already delivered host copies MUST be explicitly excluded. Acceptance: Story 1 scenarios 2 and 5, power-interruption qualification, and SC-009.
- **FR-007 — Period and expiry correctness**: Evolution MUST be forward-only and use valid network-specific period information, certificate start, and permitted lifetime. Missing or regressive information MUST prevent unsafe delivery or mutation. All started certified active/staged generations MUST advance or expire; expiry MUST erase operational state and MUST NOT generate a replacement automatically. Acceptance: Story 1 scenarios 3–4 and Story 3 scenario 6.
- **FR-008 — Generation and certificate lifecycle**: New KES secrets MUST originate on-device using a suitable entropy source, with no host-selected seed or plaintext secret import. Cold-key signing MUST remain external. Certificate installation and activation MUST verify pool identity, generation key, signature, validity, and non-regressive issuance history. Staging MUST leave the active generation usable. Acceptance: Story 3 scenarios 1, 3, and 4; entropy failure produces no generation.
- **FR-009 — Retry and rotation safety**: Generation, encrypted export, and activation retries MUST reconcile the same operation and generation. Export-triggered automatic activation MUST survive service restart, wait only for valid certification, period information, and required storage cleanup, and notify connected nodes without requiring restart. It MUST NOT require separate activation approval or backup readiness. Superseded operational state MUST not reappear. Acceptance: Story 3 scenarios 1–3, 5, and 7.
- **FR-010 — Generation-time backup**: Each generation MUST produce one immutable, recipient-encrypted, origin-authenticated initial-key artifact before generation success is reported. It MUST bind device, pool, generation, verification key, and recipient. Repeated retrieval MUST return identical bytes while retained; evolution MUST NOT create historical-state exports or replacement backups. Acceptance: Story 3 scenarios 2 and 8; retrieve the artifact again after evolution and reboot and confirm byte-identical ciphertext and unchanged generation bindings.
- **FR-011 — Conventional key-file restoration**: The local restoration operation of `pico2-kes-agent-cli` MUST validate artifact identity bindings and the recovered verification key before publishing a standard owner-restricted Cardano KES signing-key file in the format required by a conventional backup block producer. It MUST work on the recipient host without a daemon or device connection. The restored key state MUST match the device's original period-zero state byte-for-byte. Backup decryption MUST not occur on the primary host. Wrong-recipient, tampered, or identity-mismatched input MUST leave no newly published usable secret file. Acceptance: Story 3 scenario 8, Story 4 scenario 8, and SC-006, including standard-format decoding and rejection cases; running or forging blocks with an actual backup block producer is not required.
- **FR-012 — Artifact retention**: An active or staged generation's artifact MUST remain retrievable across evolution and restart. Before an artifact is reclaimed, its generation and impending loss of device-side retrieval MUST be explicit to the operator. Archived external copies remain the operator's responsibility; the device is not an unlimited backup archive. Acceptance: retrieve both retained generations after reboot, and confirm reclamation never deletes the other generation's artifact.
- **FR-013 — Service lifecycle**: The host service MUST own and manage all configured per-pool node-service sockets and its management socket, reconnect after USB loss, reject the wrong device, handle shutdown/restart safely, and avoid replacing unrelated live endpoints. It MUST not stop the node or translate temporary service loss into key revocation. Acceptance: Story 4 scenarios 1–3.
- **FR-014 — Secret handling**: The primary daemon MUST retain operational keys only transiently in protected memory and MUST NOT persist plaintext keys through files, logs, swap, dumps, or diagnostic traffic. Deployment instructions MUST address node memory, hibernation, and host snapshots as well as daemon handling. Backup recipient secrets MUST remain off the primary. Acceptance: Story 4 scenario 5 and deployment review; deliberate copies by a compromised authorized host remain outside this guarantee.
- **FR-015 — Bounded failures and observability**: Healthy pools MUST remain usable during isolated pool failures or malformed/slow client traffic. Public status MUST distinguish disconnected, recovering, ready, not-yet-valid, expired, delayed evolution, and storage/entropy failures and identify affected pools without secrets. This isolation MUST NOT be represented as protection against valid destructive commands by fully authorized socket clients. Acceptance: Story 1 scenario 5 and Story 4 scenario 4.
- **FR-016 — Management authority**: Socket access MUST grant full authority over all pools, including enrollment, generation, certificate installation, activation, deletion, and shared backup-recipient changes. The management socket MUST use the same access permissions as the pool sockets; its separate endpoint exists for management operations, not a stronger authorization boundary. No additional local administrator credential, offline signature, or per-pool authorization MUST be required. Certificate signatures, lifecycle preconditions, and integrity validation remain mandatory. Acceptance: Story 2 scenarios 2 and 7.
- **FR-017 — Backup custody**: One recipient key MUST be shared across all pools, with its private decryption key held on the backup host and never supplied to the primary daemon or device. The device MUST use the configured recipient public key for every new generation. Any socket-authorized client MAY change that device-wide recipient policy for future generations; an ordinary artifact download MUST NOT override the recipient or re-encrypt existing artifacts. Existing artifacts retain their original recipient binding. Acceptance: SC-006 covers multi-pool decryption with the shared key; verify that changing the recipient affects only later generations and leaves existing artifact bytes unchanged; Story 4 scenario 5 covers primary-host secret handling.
- **FR-018 — Export-triggered activation**: The device MUST durably commit the encrypted export result and automatic activation intent before reporting export success. Once that export is committed, it MUST activate the generation as soon as a matching valid certificate, its start period, valid period information, and required cleanup permit. It MUST NOT wait for backup-host availability, external archival, recipient-side decryption, a conventional backup file, or any separate activation approval. A lost export reply MUST NOT undo the intent or prevent otherwise valid activation; the same artifact MUST remain retrievable for retry. An uncertified or future-certified generation MUST remain pending rather than displace a usable generation prematurely. Acceptance: Story 3 scenarios 1–3, 5, and 7.
- **FR-019 — Accepted hardware and honest claims**: The accepted Pico2 A2 device MUST be a supported target without an A4 upgrade requirement. Documentation MUST distinguish ordinary power-loss/operational erasure guarantees from physical extraction, invasive remanence, malicious firmware, captured-storage rollback, and secrets retained by recipients or authorized hosts. No full-system forward-security guarantee may be claimed while key0 backups remain recoverable. Acceptance: qualification records identify actual hardware and document those exclusions.
- **FR-020 — Operator utility**: The project MUST deliver a Rust utility named `pico2-kes-agent-cli` for communicating with `pico2-kes-agentd` through its management socket. It MUST support device/pool status, pool listing and enrollment, key generation, public verification-key and encrypted-artifact retrieval, certificate installation, explicit staged-generation discard, shared recipient-public-key changes, pool deletion, and reconciliation of interrupted operations. The daemon MUST remain the sole USB owner; service-connected commands MUST NOT bypass it or introduce separate authorization. The utility MUST identify affected pools/generations, distinguish success from failure or uncertainty with meaningful exit status, and preserve the existing retry and secret-handling rules. Its recipient-side restoration operation MUST run locally under FR-011, never send private recipient keys or decrypted backups to the daemon, and never require a separate activation approval. Acceptance: Story 4 scenarios 6–8, Story 3 scenarios 2 and 8–10, and SC-008. Firmware updates, arbitrary device access, and other new maintenance capabilities are not implied.
- **FR-021 — Staged-generation conflicts and discard**: A new generation request MUST be rejected while the pool's staged slot is occupied, without changing the active or staged generation. A socket-authorized operator MUST be able to discard the explicitly identified staged generation through the CLI. Discard MUST cancel its pending activation, durably remove its operational secret under the existing cleanup rules, and free the staged slot without changing the active generation. Discard MUST fail if its target has become active and MUST NOT affect a different generation now occupying the staged slot. Lost replies and retries MUST reconcile the same discard without deleting a later replacement or reviving the discarded key. Discard does not revoke externally retained encrypted artifacts. Acceptance: Story 3 scenarios 9–10 and Story 4 scenario 6.

### Key Entities *(include if feature involves data)*

- **Device**: The enrolled physical key store, with stable identity, measured capacity, fitted-storage characteristics, and public health state.
- **Pool**: A stable pool identity bound to its cold verification identity and network context, independent of a reusable device storage slot.
- **KES generation**: One generated key lineage, its verification key, current relative period, lifecycle, and active/staged role. Evolution changes period, not generation identity.
- **Operational certificate**: The externally authorized binding of a KES verification key to pool identity, issuance counter, and validity start.
- **Encrypted initial-key artifact**: Immutable recovery ciphertext and authenticated identity metadata for exactly one generation and approved recipient; not a current-state operational export.
- **Backup recipient policy**: The one device-wide recipient public key for future generations; its matching private key resides on the backup host. Existing artifacts retain the recipient used at generation time, independently of later policy changes.
- **Pool subscription**: A node's connection to its selected pool's service socket, with delivery state that cannot cross pool or generation boundaries.
- **Lifecycle operation**: A generation, activation, retirement, or policy-change intent whose result can be reconciled after interruption without repeating the mutation.
- **Period context**: Validated network parameters and current-period information, including freshness and regression status; the device is not a trusted wall clock or chain validator.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 — Capacity and isolation**: In a 64-pool qualification run, every requested pool receives a correctly bound usable current key; cross-pool deliveries are zero, and a 65th enrollment changes zero existing pools. Repeat with 64 active plus 64 staged generations.
- **SC-002 — Recovery**: Across at least 1,000 randomized hardware power interruptions covering generation, evolution, activation, and cleanup, no acknowledged/released state rolls back, no ambiguous state is silently served, and no new key or certificate is needed for a still-valid recoverable generation. Separately exercise every identified persistent transition boundary under fault injection.
- **SC-003 — Recovery time**: All 64 valid pools become available within 60 seconds after device connection, host service, valid period information, and requesting nodes are available, including required catch-up and cleanup. This is a qualification target, not a measured claim.
- **SC-004 — Normal delivery**: With all 64 active generations recovered and current, a concurrent request from each pool receives its correct usable key within 10 seconds; idle or stalled clients do not prevent that outcome for healthy clients.
- **SC-005 — Rotation continuity**: With the backup host offline, an exported replacement becomes available automatically once certification and timing permit, without separate activation approval, node restart, or changes to the other 63 pools' generations. Lost replies and restart at each export/activation boundary result in zero duplicate generations and zero reappearance of superseded keys.
- **SC-006 — Export fidelity and file compatibility**: For every generation used in the qualification rotation, including generations from different pools, decrypt its artifact using the shared recipient key and verify byte-for-byte equality with the original period-zero state generated on the device. An independent standard-format decoder MUST recover that same state from the restored conventional KES signing-key file. Every wrong-recipient, tampered-artifact, and identity-mismatch case publishes zero usable output keys. These checks require no backup block producer and do not gate activation.
- **SC-007 — Real primary-producer proof**: On a controlled network, independently verify accepted blocks from agent-backed bulk credentials before and after evolution, rotation, and complete power recovery. Missing leadership opportunities are not a pass; test setup must supply them. No accepted-block or runtime test of a conventional backup producer is required.
- **SC-008 — Operator completion**: An operator following the supplied instructions uses the installed utility for enrollment, status inspection, public-key/export retrieval, certificate installation, rotation, recipient changes, and deletion, and completes the external certification handoff, 64-pool configuration, and power recovery without undocumented intervention or handling a plaintext backup key on the primary. Every documented service-connected operation completes through the daemon; denied, unavailable, rejected, and uncertain outcomes are reported without direct-device fallback. Record the completion result and every required manual step. Backup-producer setup and operation are outside this acceptance exercise.
- **SC-009 — Secret persistence boundary**: Qualification observes zero plaintext operational-key or backup-decryption-key outputs on primary persistent storage and zero obsolete operational secrets in the device's identified secret-bearing regions after completed cleanup, using instrumented lifecycle evidence and fitted-storage read verification. This does not establish resistance to physical attacks or deletion of external backups.

## Assumptions

### User-imposed delivery constraints

- Firmware, the host service, and the operator utility are implemented in Rust. The systemd service is named `pico2-kes-agentd`; the utility is named `pico2-kes-agent-cli`. The service communicates with the device over USB and manages per-pool Unix node-service sockets plus a management socket used by the utility. The user permitted separate pool sockets to simplify node integration; the chosen design preserves the existing node-service protocol.
- The node integration target is `/home/westbam/haskell/cardano-node`. This feature includes bulk credential loading and any necessary integration to bind each entry to its pool socket; a multi-pool service-protocol extension is not required. No source files in that checkout are changed during specification.
- The physical target is the currently accepted Pico2 A2. No silicon upgrade, general HSM, or inherited A4-only production gate is required.
- Resolved authority: socket access grants all management operations across all pools. Common permissions on service and management sockets preserve this single trust boundary; there is no stronger management role.
- Resolved backup custody: the backup host holds one private recipient key shared across all pools. Compromise exposes all available artifacts encrypted to that key; neither device erasure nor later recipient replacement revokes them.
- Resolved activation: encrypted export commits automatic activation intent. No backup-readiness approval is required. Certificate validity, start period, trustworthy period information, and crash-safe cleanup remain mandatory conditions for serving a usable key.
- Resolved backup-verification scope: no separate backup-producer user story or runtime qualification is required. Acceptance ends at successful decryption, byte-for-byte equality with the device's generation-time period-zero state, and restoration to the standard KES signing-key file format.

### Defaults and scope boundaries

- This is a current-key provider, not an external signing service: authorized nodes hold evolved KES state and sign locally. A compromised authorized client can copy that state and derive later states in that generation; receiving period zero is as powerful as recovering the initial-key backup.
- Persistence means nonvolatile device storage, not SRAM surviving loss of power. Raw storage layout, cryptographic suites, USB class, firmware framework, and service message encoding belong in the implementation plan, not this specification.
- One daemon manages one device. The capacity commitment is 64 simultaneous pool subscriptions, one per pool; redundant subscriber topology beyond that is not an additional capacity commitment. A backup uses the conventional file method. Remote forwarding and distributed fencing are outside scope.
- Each pool is bound to its own network context; no mainnet timing constants are assumed. The operator supplies trusted host time and local network information. A hostile authorized host can cause availability loss or premature advancement; the device does not validate the chain independently.
- One active plus one staged generation per pool is required for non-disruptive rotation. The staged slot covers generation/export preparation and waiting for valid certification or its start, not a backup-approval queue. An occupied staged slot is never overwritten implicitly: the operator must explicitly discard its identified generation before generating another replacement. Increasing the pool count MUST NOT be satisfied by reducing this to a shared replacement slot.
- New generations originate on-device. Migration occurs at a normal fresh-key/certificate rotation; importing an existing plaintext KES key or restoring backups into the device is excluded.
- Cold keys, certificate issuance and issuance-counter administration remain in the operator's existing external workflow. VRF secrets remain with the node and are not moved into this device.
- The utility's local restoration operation creates the explicitly requested conventional secret file on the backup host using its shared recipient private key, without a service connection. The file-based backup retains the ordinary method's weaker erasure properties. Encryption protects an artifact from non-recipients; it does not remove the recipient's ability to reconstruct earlier periods.
- Export-fidelity qualification uses disposable keys and test-only access to the original period-zero state in protected device memory. Compare against that generation-time state, not the device's later evolved state, and discard the test copy after comparison. This adds no production plaintext-export command or retained initial-state recovery copy. File-format checks use an independent standard-format decoder, not a running backup producer.
- Cloud upload scheduling, cloud account management, failover/failback automation, and prevention of simultaneous primary/backup forging remain external responsibilities. Device activation never waits for evidence from those workflows.
- Firmware installation uses attended trusted maintenance. Remote updates, a custom bootloader, fleet management, mandatory fuse programming, and a general offline-management framework are not inherited from the old plan. No irreversible device operation is authorized by this specification task.
- The 10-second delivery and 60-second recovery bounds are proposed acceptance targets derived from the earlier plan and raised to the requested 64-pool scope; hardware feasibility must be demonstrated, not assumed. The old 32-pool memory/flash layout is not evidence that 64 pools fit.
